# 修改记录（modifications）

> 与 `CHANGELOG.md` 的分工：CHANGELOG 面向使用者、只写「做了什么」；
> 这里面向改代码的人，写「为什么这么做、根因、改法、位置、验证、遗留」，便于下次快速锁定问题。

## 目录
- `by-version/` —— 按版本 + 轮次，一次 git 提交一篇（`v1.2.5-r1.md` …）。想知道「这一版整体改了什么」看这里。
- `by-feature/` —— 按功能线，同一功能的历次改动**追加在篇首**（`reader-flip.md`、`reader-compare.md` …）。
  想知道「这块为什么这样写 / 上次踩的坑」看这里，**优先用这一份**。

## 查找规矩（重要，防止浪费时间）
1. 先按功能名打开 `by-feature/` 里对应的那**一篇**；不要遍历目录，更不要全仓 grep。
2. 功能名不确定时，先看 `docs/feature-index.md` 第 1~8 节定位功能线，再回来读那一篇。
3. 只有做版本验收 / 回滚时才读 `by-version/`。

## 每篇记录的小标题（统一，便于扫读）
```
## YYYY-MM-DD · v{版本}（第 N 轮）
- 需求：用户原话要点
- 根因：为什么会坏 / 为什么原来做不到
- 改法：怎么改的（关键手法、取舍）
- 位置：文件 + 符号（不用写行号，行号会漂）
- 参考：查到的外部结论与出处线索（库名 / 规范名）
- 验证：跑过什么、看到什么（L0/L1/L2 哪一档）
- 遗留：已知风险、下次要注意什么
```

## 编排与容量规则

- `by-version/` 与 `by-feature/` 都使用“最新内容在最上方”；同一功能线按日期、版本和轮次倒序。
- 一篇功能记录只保留当前仍有助于定位和排障的内容。历史轮次写“当时状态”，发布后不回写为“已发布”。
- 当前容量上限：`feature-index.md` 130 行 / 20 KB；单篇功能记录 180 行 / 26 KB；
  单篇版本记录 120 行 / 14 KB。达到 80% 时先压缩重复描述。
- 功能记录超过上限时，新建 `docs/modifications/archive/by-feature/`，
  将较早轮次移入归档文件；现行篇首保留最近决策、当前风险、归档链接。
- 每次提交前运行 `npm run check-docs`。检查 UTF-8 / CRLF、本地链接、容量、
  误写的字面量换行和功能记录倒序。
